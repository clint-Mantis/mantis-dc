## 1. Role and goal

You are the lead engineer rebuilding the **B-BBEE Data Capture (DC) repository** of the Mantis Networks client portal. The current module is a Laravel + Livewire app at `portal.mantisnetworks.co.za/client/dc`. Nobody can maintain it and the source code is not available, so this is a clean rebuild from the specification below.

Build **Phases 1–3** only:

1. **Foundation**: auth, organisations, roles, lookups, the project wizard, and RLS.
2. **Capture engine**: one metadata-driven form and grid engine that serves all 8 capture pillars, with CSV/XLSX import and export and copy-forward.
3. **Evidence and verification**: file evidence in Supabase Storage, an evidence checklist, verification sampling, verifier queries, record locking, and an audit log.

Out of scope for now: migrating legacy data, scorecard points and level calculation, and PDF scorecard packs. Design the schema so these can be added later without breaking changes.

## 4. Domain primer (read carefully)

- A **client organisation** (e.g. a corporate) is measured once per financial year for a B-BBEE scorecard. Each measurement is a **project**.
- A project has a **sector code**: DTi Generic, Construction, Finance, ICT, Property, AgriBEE, Defence, or MAC (Marketing, Advertising & Communication). It also has a **size**: EME, QSE, or Generic. The sector code changes which fields apply on some pillars.
- Data is captured in **pillars**: Financial, Ownership, Management Control, Skills Development, Enterprise & Supplier Development (ESD), Suppliers (preferential procurement), Socio-Economic Development (SED), and Y.E.S. Initiative.
- A **verification agency** later samples rows and checks evidence. Today evidence is only Google Drive links. In the new build evidence becomes real files attached to the project, a pillar, or an individual row.
- Users today switch between client "profiles". In the new build this becomes organisation **memberships** with roles.

## 5. Roles and access

| Role | Scope | Can |
|---|---|---|
| `mantis_admin` | all orgs | everything, including config tables (sector codes, lookups, field metadata) |
| `consultant` | orgs they are assigned to | create and edit projects, capture data, manage evidence, lock and unlock pillars |
| `client_editor` | own org | capture and edit data and evidence on unlocked projects/pillars |
| `client_viewer` | own org | read only; ID numbers and salaries masked |
| `verifier` | projects they are added to | read data and evidence, select samples, raise and close queries; cannot edit capture rows |

Store roles in `memberships(user_id, org_id, role)`. Users get project-level access through `project_members(project_id, user_id, role)`, where verifiers are added per project.

## 6. Data model

Use the `public` schema for tables and a `dc` schema for helper functions. Every capture table has these standard columns:

`id uuid pk default gen_random_uuid()`, `project_id uuid not null references projects on delete cascade`, `created_at timestamptz default now()`, `created_by uuid default auth.uid()`, `updated_at`, `updated_by`, `sample_selected boolean default false`, `verification_status text check in ('unverified','sampled','queried','verified','rejected') default 'unverified'`, `row_locked boolean default false`, `source text check in ('manual','import','carried_forward') default 'manual'`, `import_job_id uuid null`.

Add an index on `project_id` for every table that has it.

**Types:** money is `numeric(18,2)`, percent is `numeric(7,4)` in the range 0–100, counts are `integer >= 0`, and "Yes/No" fields are `boolean`. Every dropdown is a FK to `lookups` (`lookup_id uuid`) unless it is listed as an `enum` (use a `text` column with a check constraint).

## 8. Functional requirements

### Phase 1: Foundation

1. Email + magic-link login, with a profile page.
2. An organisation switcher in the header that replaces the legacy profile dropdown. Admins and consultants see their orgs; client users see only their own.
3. An admin area (mantis_admin only) for organisations, divisions, users and memberships, sector codes, products, lookups, field metadata (read-only table view is enough in Phase 1), and evidence templates.
4. **Project list** per org, showing title, division, FY end, sector, size, status, and progress. There's also a **project wizard**:
   1. Organisation and division (pick or create).
   2. Financial year end. Derive period start and end, plus a label such as "FY2026 (Mar 2025–Feb 2026)".
   3. Product, sector code, and size.
   4. Copy forward from a previous project (optional; Phase 2 implements the copy).
   5. Team: consultant, client users, verifier, data deadline, verification date.
   6. Create. This generates `evidence_checklist_items` from the templates and `pillar_status` rows.
5. A **project dashboard** with one card per pillar: rows captured, rows with missing required fields, evidence items outstanding, and locked state.
6. Write **RLS** for every table in section 6. Create a `security definer` function `dc.has_project_access(project_id, min_role)` and `dc.has_org_access(org_id, min_role)` that read memberships and project_members. Policies use only these helpers. Writes to capture tables are refused when the pillar is locked or `row_locked` is true, unless the user is a mantis_admin or consultant. Viewers get the masked views `v_people_masked` (ID number shows only its last 4 characters; monthly salaries and stipends are null).
7. **Gate 1:** pgTAP tests prove, for each role, that the user can read and write exactly what section 5 says and nothing across organisations.

### Phase 2: Capture engine

1. A generic `<PillarPage pillar="…">` reads `dc_field_defs` and `dc_field_rules` for the project's sector and renders:
   - **Grid:** virtualised, with column groups (`group_name`), a sticky first column, sort, filter, column chooser (saved per user in localStorage), row checkbox for sampling, and row actions (edit, delete, evidence, queries).
   - **Side-panel form:** fields shown or hidden and relabelled live from the rules. Validation is Zod, built from the metadata (type, required, ranges). The same rules are enforced again in Postgres (check constraints, plus a `dc.validate_row` trigger for conditional-required rules).
   - **Toolbar:** Add, Import, Export CSV, Export XLSX, Export selected samples, and Delete selected. Delete selected needs typed confirmation and is allowed only on unlocked pillars.
2. **Financial** uses a single-record form with the two mini grids (history, SDL months) instead of a list.
3. **People, beneficiaries, and supplier masters** each have a searchable picker with inline create. Editing a person updates them everywhere they're used.
4. **Import (Edge Function `dc-import`):** upload CSV or XLSX to Storage, then auto-map headers to fields (by label or key, including the legacy labels in section 7), then let the user adjust the mapping. The function validates every row and returns errors per row and column. The user previews, then commits only the valid rows (or all-or-nothing, which is the user's choice) as one transaction. Store everything in `import_jobs`. Offer a **"Download template"** XLSX per pillar, generated from the metadata, with dropdown validation lists.
5. **Export (Edge Function `dc-export`):** XLSX per pillar, or all pillars as sheets in one workbook, with the labels from the metadata. It can also export only the selected sample rows.
6. **Copy forward:** the Postgres function `dc.copy_forward(from_project, to_project, pillars text[])` copies Ownership, Management Control, and Suppliers rows, plus beneficiaries referenced in ESD and SED. It sets `source = 'carried_forward'`, and the UI shows a "confirm" badge until each row is edited or confirmed.
7. **Gate 2:** seed the Demo project from `seed.sql` (3 shareholders, 10 MC members, 10 suppliers, plus a few rows in every other pillar). A Playwright test captures, edits, imports, and exports in every pillar without errors.

### Phase 3: Evidence and verification

1. **Evidence panel** on the project, on each pillar, and on each row. It supports drag-and-drop upload to the `evidence` bucket, a preview for PDFs and images, download, and a status (pending, accepted, rejected) with a note. Storage RLS uses the same access helper by parsing `project_id` from the path.
2. **Evidence checklist** per project, generated from templates. Items can be marked accepted or rejected by a verifier or consultant, and they show progress on the dashboard.
3. **Sampling:** the verifier ticks rows (`sample_selected`) or uses "random sample n rows per pillar". Sampled rows get `verification_status = 'sampled'`. Add a "Samples" view across pillars.
4. **Queries:** the verifier raises a query on a row, and the client answers in the row side panel. Show open query counts on the grid and dashboard. Status moves from open to answered to closed.
5. **Locking:** a consultant can lock or unlock a pillar, and the verifier can mark rows verified or rejected. Locked pillars are read-only for client roles.
6. **Audit:** a history tab per row and per project, read from `audit_log`, showing who changed which field from what to what.
7. **Gate 3:** a Playwright test runs a full cycle. The client captures data and uploads evidence, the verifier samples and raises a query, the client answers, the verifier verifies, and the consultant locks.

## 9. Non-functional requirements

- Personal data (POPIA): don't log ID numbers or salaries anywhere, mask them for viewers, and use the private bucket only (signed URLs that expire in 10 minutes).
- Performance: a 10,000-row supplier grid must load and scroll smoothly. Use server-side pagination or range queries if needed, plus indexes on `project_id` and on common filter columns.
- Accessibility: every form field has a label, the UI is keyboard-navigable, and focus states are visible.
- Run `supabase db lint` and the Supabase security advisors with zero errors before each gate.
